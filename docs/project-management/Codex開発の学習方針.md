# ゲーム制作を通じたCodex開発の学習

2026-10-11、ユーザーが明示したテーマを整理。

## このチャットの目的

ADV「探偵 佐伯湊」の制作を進めながら、Codexでの開発の流儀を身につける。ゲームの完成と、依頼・実装・検証・レビュー・統合の実践経験を両方の成果とする。自動化や管理の仕組みを増やすこと自体を目的にしない。

ユーザー確認: 今回の制作は、完成後に共通化するMinatoEngineと、ストーリー相談から人物画像生成・採用・組み込みを支援するエージェントのベース作り。ゲームを進める各段階で、設定・素材・処理の対応と再現できる手順を残し、実際に有効だった部分を後から再利用する。

## 役割

- ユーザー: 作品の方向、優先順位、体験の良し悪し、未確定仕様、最終採用を判断する。
- このチャット: 進捗と依存関係を整理し、次の作業の範囲・完了条件・統合方針を明確にする。手戻りから運用を改善する。
- UI作業: saeki-ui-windowsでUIと必要なシステム変更を調査・実装・検証する。
- 素材作業: saeki-talk-issue5でキャラクター等の資料・素材を制作する。

チャットの担当分けだけでは変更を隔離できない。コード変更はチェックアウトとブランチで分け、全体の正本は既存仕様・ロードマップ・Issueを使う。他チャットへ指示を送る際はユーザーの明示的な依頼に従う。

## 身につける基本サイクル

1. 目的を決める: プレイヤーの何が改善されるか。
2. 現状を調べる: 関連仕様・コード・既存テストを読み、重複実装を避ける。
3. 作業を絞る: 対象範囲・制約・完了条件を定める。複雑な作業は先に計画する。
4. 実装を任せる: 調査から必要な検証までを一つの依頼に含める。
5. 結果を確認する: 自動テスト、差分レビュー、人間のプレイ確認を区別する。
6. 統合する: 採用した変更をコミット・PRなどの追跡できる単位で取り込む。
7. 一つ学びを残す: 追加指示、手戻り、役立った完了条件を短く記録し、必要な共通ルールだけ更新する。

## 今の評価

- 有効: 素材とUIの作業場所を分離した。最新mainを基点にUI環境を整えた。実際にWindowsでビルド・テストを確認した。
- 今後必要: 小さな実装タスクを一件、依頼から検証・プレイ確認・統合まで通して経験する。
- 未達: 今回の環境整備だけでは、Codex開発の全工程や自律開発方式を習得したとは判断しない。
- 環境: WindowsとWSLのどちらを使うかは開発環境の選択。Codexでの開発の本質は、目的・文脈・完了条件を渡して変更と検証の証拠を確認すること。

## 学習の記録

各タスク終了時に以下を短く記録する。

- ゲームで改善したこと。
- Codexに任せて完了した工程。
- 追加指示や仕様判断が必要だった点。
- 検証結果と未検証範囲。
- 次回も使う依頼方法、または一つだけ変える運用。

Issue・PR・テスト等の証拠があれば添える。所要時間や追加指示数は実測できる範囲だけ記録する。

## 直近の実践

UI側で未完の改善を一件選び、最新実装と照合してから、目的・対象・完了条件を決める。その一件を実装・自動検証・差分確認・ユーザーのプレイ確認まで進める。繰り返して安定した作業だけ、後からスキルや自動化の候補にする。

参考: https://learn.chatgpt.com/guides/best-practices

ユーザー方針: ベストプラクティスに沿って進める。標準運用と依頼テンプレートは[開発タスクの型](開発タスクの型.md)を使用する。

## 現在の運用の監査と軌道修正

2026-10-11、ローカルコード・CI・Issueテンプレートと直近のUIチャットを確認。

評価: 開発基盤は推奨に沿っているが、実作業の単位と完了・統合の運用に中程度のずれがある。公式の点数基準はないため数値評価はしない。

確認済みの強み:
- AGENTS.md、正本のUI仕様、受入条件を含むIssueテンプレートがある。
- 既存CIはPR/main pushでNodeテスト・型チェック・ビルドを実行する構成。
- 過去にPRによる取り込み履歴がある。今回もWindowsで74件成功とビルド成功を確認した。
- 素材とUIは別ブランチ・別チェックアウトに分離した。

ずれと修正:
- UI等の役割名の長いチャットへ複数の成果が蓄積。次のコード変更から具体的な成果一件に範囲を絞り、独立する成果は別作業チャットで扱う。素材の基本デザインのように同じ問題の比較・反復は継続してよい。
- ユーザーがチャット間の転送役を担う。共有する仕様・Issue・結果を正本へ残し、依頼は参照先と目的を中心に短くする。自動連携はまだ導入しない。
- 管理資料を短期間に増やした。今後この学習方針、進行管理、タスクの型を中心に更新し、毎回新しい管理ファイルを作らない。既存の調査結果・環境案内は参照資料として保持。
- UIで24件のブラウザーテストをスキップ。次のUIタスクの完了条件に必要なブラウザー検証を含める。
- 環境移行の学習記録がUIブランチに未コミット。次の機能変更とは分けて扱う。無関係な変更を一つのPRに混ぜない。
- UI側の会話で決まった未完作業と現在Issueの対応、最新CI結果・保護設定はまだ未確認。次の主タスクを決める際に確認する。

直近の順番: 未完UI作業を一件に絞る → 既存Issue・仕様・コードと照合 → 完了条件を決める → 調査・実装・自動検証・ブラウザー確認 → 差分レビューとユーザーのプレイ確認 → PRで統合 → 学びを一つ記録。

今は管理の拡張を止め、上記の一周をゲームの具体的な改善で実践する。
