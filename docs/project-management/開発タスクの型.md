# ADV開発タスクの型

2026-10-11。公式ベストプラクティスを、このプロジェクトでの実践手順へ具体化したもの。公式に指定された唯一の構成ではない。

## 運用の標準

- ここは全体の優先順位・依存関係・統合と学習の管理。実装の詳しい文脈は成果単位の作業チャットに置く。
- 作業の正本は既存の仕様書・ロードマップ・Issue。チャットで決めた仕様は関連資料へ反映し、同じ仕様を複数ファイルに二重管理しない。
- 変更は目的単位で絞る。複雑・曖昧な変更は調査と計画を先に行う。小さく明確な修正はそのまま実装・検証まで進める。
- 共通ルールは短いAGENTS.mdに置く。タスクごとの条件はIssue等へ置く。
- 並行するコード変更は別ブランチ・別チェックアウトで隔離。今は既存の独立cloneを使い、今後の同一リポジトリ内の並行作業は適切なworktreeを検討する。
- 実装後は関連テスト・型チェック・ビルドと差分レビューを行う。UIはブラウザーで結果を見る。プレイ確認と自動検証は別に報告する。
- 実装の説明だけで完了としない。未実行の検証があれば完了条件の未達として記録する。
- 取り込み前にレビューし、ゲーム体験はユーザーが確認する。コミット・PRで変更を追跡する。mainへの直接コミット・自己マージは既存ルールに従う。
- CIは既存の.github/workflows/ci.ymlを利用する。PRとmainへのpushでNode 24、npm ci、Nodeテスト、型チェック・ビルドを実行する構成を確認済み。実際の最新実行結果は未確認。外部Chromiumを用意していないためブラウザーテストの実行は別途必要。
- 繰り返して安定した方法をスキル化・自動化する。必要な外部情報の手動転送が負担になった時点で接続ツールを検討する。

## 依頼テンプレート

```text
目的：プレイヤーが［何を］できるようにする。
作業先：saeki-ui-windows（開始時にブランチと未コミット差分を確認）
関連情報：［Issue / 仕様書 / 再現手順 / 対象画面］
対象範囲：［今回変えること］
制約：既存仕様・セーブ互換性を維持。［今回含めないこと］
完了条件：［具体的な操作と期待する結果］
検証：関連テスト、型チェック・ビルド、［必要な画面・入力確認］。

関連コードと既存実装を調べ、重複実装を避けてください。
複雑な場合は先に計画し、仕様判断が必要な点だけ相談してください。
実装と必要な検証まで進め、最後に差分をレビューしてください。
報告は変更・検証結果・未検証範囲・残課題を簡潔にまとめてください。
```

## タスク終了時の確認

1. 受入条件を満たしたか。未達なら何が残るか。
2. テスト・ビルド・画面確認の実際の結果は何か。
3. 変更範囲は目的と一致するか。別系統の変更と競合するか。
4. 採用・統合に必要な判断は何か。
5. 今回学んだCodexの任せ方を一つ記録する。
