# AI開発方式・学習記録

このディレクトリはゲーム制作（Track A）とは別に、AIを活用した開発体制の変化（Track B）を学習資産として残す。

- [evolution.md](../07-decisions/ai-development.md): 開発方式の段階、移行理由、実績と計画
- [experiments/EXP-001-issue-driven-development.md](experiments/EXP-001-issue-driven-development.md): Issue駆動型の自律開発実験（計画）

## 記録の原則
以下の現行運用を優先する。実験資料やevolution.mdの過去の方式は履歴・計画であり、毎回Issueを作成する義務ではない。
- 実施済み、確認済み、計画、仮説を明確に区別する。
- 成功だけでなく、失敗、追加指示、手戻り、制約を記録する。
- 変更の理由と比較対象（以前の開発方式）を残す。
- Issue、PR、コミット、テスト結果へのリンクを付ける。
- AIが記録案を作り、人間が判断理由と解釈を確認する。
- 機密情報や認証情報を記載しない。

ゲーム制作の進行を優先し、記録作業は必要最小限とする。

## PM主導の標準運用（2026-10-13）

ユーザーはプレイ中の不具合・気になる点・改善要望を自由な文章で「プロジェクト管理」へ報告する。担当指定、Issue要否、制約の再記載は不要。PMは以下を実施する。

1. 複数の指摘をまとめて受け付け、不具合・改善要望・作品/仕様の判断事項へ分類し、再現情報、影響、依存関係、優先順位を整理する。足りない情報だけ確認し、不要な全件調査をしない。
2. 独立して完了・検証できる小さな単位に分け、必要な専門担当だけに目的・対象範囲・完了条件・依存関係を示して依頼する。必要な実装・関連テスト・コミットまでを一区切りとし、すべての項目を一度に実装せず、PMが区切りごとに成果を確認して次の単位へ進む。既存仕様内の修正は担当が自律実施し、重要な作品方針・仕様変更はPMがユーザーへ確認する。
3. 今回完結できる軽微な修正は原則Issueなし。未完了の持ち越し、ユーザー判断待ち、複数担当での継続調整、大きな機能変更、再発など継続追跡が必要な場合はIssue化する。PMにこの判断と作成を委任する。関連事項は必要に応じてまとめ、既存Issueを必要最小限確認して再利用する。
4. 担当の成果・検証結果をGitHubのコミットまたはPRに残す。Issueなしでも変更内容・検証結果・未確認事項を記録する。修正不要の場合はその根拠を報告し、記録のためだけにコード変更やPRを作らない。
5. PMがGitHubと担当報告を照合し、結果・未完了事項・必要なユーザー判断を簡潔に報告する。持ち越しは既存/新規Issue等の追跡先を示し、未確認を完了扱いにしない。

## 既存4担当の責務と境界

| 担当 | 責務・自律判断 | 連携・判断の境界 |
| --- | --- | --- |
| プロジェクト管理（PM） | 要望受付、分類・優先順位・担当・Issue要否の判断、依頼、GitHubで成果/進捗確認、依存関係と追跡先の管理、結果集約 | 重要な作品方針・仕様変更と採用判断はユーザーへ確認。不要な担当起動・重複調査を避ける |
| システム開発 | React/TypeScript/CSS実装、既存仕様内の軽微なUI/不具合修正、画面遷移・動作・性能検証、必要なテスト/ビルド、コミット/PR、実装状態の台帳更新 | UI方針変更はPMへ相談。UI仕様を受けて実装し、物語の設定や原稿を独断で変更しない |
| UI・デザイン | UI/UX設計、レイアウト・配色・画面構成、操作性・視覚演出、アイコン/UIパーツ、実装に渡すUI仕様 | 再設計が必要な場合にPMから依頼。軽微な既存仕様内修正には必須参加しない。実装はシステム担当 |
| ストーリー構成 | シナリオ・人物設定・台詞・分岐・演出意図・物語全体の整合性、原稿正本 | 物語上の判断が必要な場合のみ参加。必要なUI情報・演出意図はUI担当へ共有。ゲーム接続はシステム担当 |

物語のUI要件→UI設計→システム実装の必要な部分だけ連携し、PMが依存関係を整理する。全案件で全担当を起動しない。既存仕様と資料の矛盾はPMに報告し、推測で仕様を確定しない。

## セッション管理方針

- PM・専門担当の役割は本書とAGENTS.mdで維持し、特定のチャット履歴に依存させない。4担当という役割構成と、セッションの交代は区別する。
- 新規の独立したタスクでは原則として新規担当セッションを作成する。同一タスクの継続、同じPRの追加修正、検証失敗への対応は既存セッションを優先する。軽微な追加指摘ごとにセッションを作り直さない。
- PM自身も、進捗・未完了事項・判断待ち・追跡先をGitHubの既存台帳・Issue・PRへ保存したうえで、新規セッションへ交代可能とする。ユーザーの依頼窓口という役割は維持する。
- 新規セッションへの引き継ぎは、役割、目的、完了条件、関連資料、ブランチ/PR、未完了事項だけに絞る。必要な作業場所・基点SHA・未コミット変更の所在・承認待ちは関連資料や未完了事項に記録し、長い会話履歴やログ全体を渡さない。未完了の変更を失う状態で交代しない。
- PMは受付・担当選定・依頼・結果集約を担い、詳細なコード調査は専門担当へ委譲する。GitHub上の成果・検証記録を引き継ぎ元とし、完了済みの調査・テストは不要に繰り返さない。双方とも必要な資料だけを読み、不要な全件調査、長いログの取得、繰り返しの進捗確認を避ける。
- 必要なセッション交代は、不要なサブエージェント起動や担当追加とは区別する。新規セッションの作成と資料からの役割・制約・PR状況の把握は検証済みであり、実装作業そのものの引き継ぎは未検証。新規チャット作成時は利用可能な機能のユーザー指示・権限条件に従う。
- Codex利用枠の節約効果は未検証。セッション交代による利用枠の回復を前提にしない。既存のIssue判断、承認ルール、役割分担、画像生成保留は維持する。

## 現在の制約

- 人物立ち絵・背景・イベントCGの新規生成は保留。過去の制作依頼・生成手順は再開許可にならない。
- アイコンは既存ライブラリやCSS/SVGを優先する。
- 新規サブエージェントの不要な起動、広範囲の再調査、コンテキスト圧縮を避ける。既存4担当を維持する。
- mainへの直接コミット、PRの自己マージ、破壊的操作は既存AGENTS.mdの明示許可条件を維持する。依頼・PR作成の許可をマージ許可と扱わない。
- この運用整備そのものはゲーム改修・画像制作の着手依頼ではない。
